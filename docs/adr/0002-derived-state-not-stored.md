# 状态一律派生，只持久化事实

本插件里绝大多数“状态”都是其他数据的函数：任务状态（待办/进行中/完成）由 `progress.current/total` 派生、逾期由截止日与完成时间派生、看板**格**完成数由当日条目派生、目标进度由会话派生、配速由时长与里程派生、连续（streak）与完成率由历史日文档派生。我们决定**全部不落库**，只持久化不可推导的事实——时间戳、指标、条目本身、以及流水量的存量值。理由是存储状态必然引入漂移：任何一条写路径漏更新，存储与事实就永久不一致；而读路径是内存上的同步迭代（storage domain 的读来自权威内存态），几十天到几年的重算成本可以忽略。这条原则同时让“补卡后 streak 即时重算”“改目标只影响之后的日子”这类行为自然成立，而不是特例逻辑。

- **Status**: accepted
- **Considered Options**
  - 存储状态字段（如 `tasks.state`、`days.completionRate`）—— 需要每条写路径维护一致性，且与补卡即时重算直接冲突。
  - 物化缓存 / 汇总表 —— 在单用户个人工具的数据量下是纯负担，还多一份可能漂移的真相。
- **Consequences**
  - 统计与状态在宿主侧按需重算；聚合本就放在宿主，不增加跨进程成本。
  - schema 更窄、演进更容易：新增派生规则不需要回写历史数据。
  - 派生规则成为核心逻辑，必须有单元测试覆盖（尤其 4 点界线、向前继承、空白天中断连续、任务三态、配速）。
